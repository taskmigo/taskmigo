## Internal clients

Phase 1 system-managed registrations are confidential service clients using `client_credentials`. They are declared in
server configuration and reconciled into PostgreSQL during startup. They are not editable through an HTTP management API.
Removing a declaration does not delete its database registration; disable it explicitly instead. Interactive client fields
are added with the interactive login phase rather than being accepted before they are supported.

## Built-in CLI client

The `cli` registration is the first system-managed client. It uses `client_credentials` and is also a service principal.
The client requires both the `taskmigo.api` scope and the `system.resources.manage` service permission to access
`/api/v0/**`.

Scope alone is insufficient. This prevents a newly registered machine client from gaining resource-management access merely
by requesting an API scope.

Provide every field explicitly. No client ID, secret, enabled state, or generation is inferred:

```bash
export TASKMIGO_INTERNAL_CLIENTS_0_ID=cli
export TASKMIGO_INTERNAL_CLIENTS_0_SECRET='replace-me'
export TASKMIGO_INTERNAL_CLIENTS_0_ENABLED=true
export TASKMIGO_INTERNAL_CLIENTS_0_GENERATION=1
```

Add another client by using index `1`, then `2`, and so on. The server rejects incomplete definitions and duplicate IDs.
Each declared ID is the upsert key.

## Persistent protocol state

The following state is stored in PostgreSQL and survives application restarts:

- registered clients and their encoded secrets;
- issued authorizations, including access and future refresh tokens;
- authorization consent;
- internal-client management metadata in the registered client's `client_settings`.

The migration copies the three JDBC schemas distributed by Spring Authorization Server, with only the library-prescribed
PostgreSQL substitutions (`timestamp` to `timestamptz` and `blob` to `text`). Taskmigo does not add OAuth tables, foreign
keys, or indexes.

An idempotent reconciler inserts or updates by client ID without changing the internal database identifier. Every definition
has an explicit monotonic generation. Increase it whenever the secret or enabled state changes:

```bash
export TASKMIGO_INTERNAL_CLIENTS_0_GENERATION=2
```

An older application instance cannot overwrite a newer generation during a rolling deployment. Two different definitions with
the same generation are rejected. An unchanged secret retains its encoded value. An existing client not marked as
Taskmigo-managed is never adopted implicitly.

Expired `client_credentials` authorizations are removed periodically. The cleanup interval and retention window default to
one hour and seven days and can be configured with `TASKMIGO_OAUTH_AUTHORIZATION_CLEANUP_INTERVAL` and
`TASKMIGO_OAUTH_AUTHORIZATION_RETENTION`.

## Signing key

JWTs are signed by an externally provisioned RSA private key stored in a PKCS#8 PEM file. Production startup fails if the
configured file does not exist. Every instance must mount the same key material; sharing only the key ID is insufficient.

```bash
export TASKMIGO_OAUTH_SIGNING_KEY_FILE=/var/lib/taskmigo/oauth-signing-key.pem
export TASKMIGO_OAUTH_SIGNING_KEY_ID=primary
```

The container defaults to `/var/lib/taskmigo/oauth-signing-key.pem`. Mount a managed secret at that path. Replacing or losing
the file invalidates tokens signed by the previous key. Development and test environments may opt into local generation:

```bash
export TASKMIGO_OAUTH_SIGNING_KEY_AUTO_CREATE=true
```

Do not enable automatic generation for a multi-instance deployment.

The database never stores the private signing key.

## Future interactive clients

Each independently deployed frontend receives a separate registration. Interactive login will add OpenID Connect and
Authorization Code with PKCE in a later phase. It must not reuse the CLI registration because user-delegated and machine
credentials have different grants, permissions, rotation, and audit lifecycles.
