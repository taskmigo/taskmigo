---
title: Local Kubernetes
description: Build and run the complete Taskmigo stack in Minikube for local development.
---

Use this setup when you need the deployed system rather than one application process. Taskfile builds the application
images directly in Minikube's containerd runtime, deploys the Helm release, and verifies the complete stack. There is no
host-side Docker build and no `minikube image load` step.

For faster work on one JVM or Node.js process, use [Local development](/docs/v0/developer/local-development) instead.

## What this starts

The local stack contains:

- PostgreSQL `18.4-alpine` inside the Taskmigo namespace;
- Envoy Gateway `1.9.1` as the Gateway API controller;
- the Taskmigo bootstrap Job, which owns Flyway migrations and installation-state reconciliation;
- the Taskmigo web and worker deployments;
- the Taskmigo browser client;
- one `Gateway` plus separate `HTTPRoute` resources for the client and web server.

## Prerequisites

Install these host tools:

- Docker Desktop or Docker Engine for the Minikube Docker driver;
- Minikube;
- Helm 4 or a compatible Helm 3 release;
- [Task](https://taskfile.dev/docs/installation/);
- `curl` for the public endpoint checks.

The pipeline uses Minikube's built-in `kubectl`. Java and Node.js are not required for deployment because the application
builds run inside Minikube.

Taskmigo local Kubernetes requires containerd. Start the default profile with:

```bash
minikube start -p minikube --container-runtime=containerd --cpus=4 --memory=6000m
```

Taskfile checks the active node runtime before building and fails if the selected profile does not use containerd.

## Deploy

Run from the repository root:

```bash
task kubernetes:deploy
```

The deployment pipeline:

1. Waits for Minikube to become ready.
2. Uses `minikube image build` to build the bootstrap, web, worker, and client images directly into containerd.
3. Starts PostgreSQL and Envoy Gateway.
4. Installs or upgrades the Taskmigo Helm release.
5. Restarts the runtime deployments so a rebuild is picked up even when the application version has not changed.
6. Verifies workloads, routes, Flyway state, and public endpoints.

The default `task` command runs the same deployment pipeline.

### Image versions

Local images use the application version rather than a special integration tag:

- `taskmigo-bootstrap:<server project version>`;
- `taskmigo-web:<server project version>`;
- `taskmigo-worker:<server project version>`;
- `taskmigo-client:<client package version>`.

The three Gradle applications currently inherit their project version from `server/build.gradle.kts`. The client version comes
from `client/package.json`. Taskfile reads these values when it builds and deploys the images.

### Image pull policy

The reusable Helm chart keeps `IfNotPresent` as its default. The local Taskfile overrides all four Taskmigo workloads to
`imagePullPolicy: Never`.

This is intentional: the images already exist in Minikube's containerd image store, and a missing image should fail instead
of pulling an image with the same name from a registry.

## Terminal workflow

No Docker environment variables are required. In particular, do not run `eval "$(minikube docker-env)"`: that workflow is
for Minikube's Docker runtime, while Taskmigo requires containerd.

Every terminal can run Taskfile commands independently because each `minikube image build` command targets the selected
Minikube profile explicitly. Opening or closing another terminal does not change the image build environment.

A normal development session is therefore:

```bash
minikube start -p minikube --container-runtime=containerd --cpus=4 --memory=6000m
task kubernetes:deploy
```

If Minikube is already running, only the second command is required.

To inspect the images stored in Minikube:

```bash
minikube -p minikube image ls
```

## Access the local deployment

The Gateway publishes one origin, `http://taskmigo.internal.com`: `/api/auth` is owned by the client BFF; API and OAuth
paths are routed to the backend; and all other paths are routed to the browser client.

Taskfile injects this hostname into the client pod and uses explicit address resolution for deployment verification. Add
the same mapping on the development host before opening a browser:

```bash
minikube_ip="$(minikube -p minikube ip)"
printf '%s taskmigo.internal.com\n' "$minikube_ip" | sudo tee -a /etc/hosts
```

The final output prints the public URL, API and OIDC paths, required host entry, and bootstrap login. The default local
credentials are deliberately simple and must never be reused outside a disposable development cluster:

```text
Username: system
Password: taskmigo
```

Credentials are created only when `taskmigo-secrets` does not exist. Override them on the first deployment when needed:

```bash
BOOTSTRAP_USER_PASSWORD='replace-me' \
AUTH_SESSION_SECRET='replace-with-at-least-32-characters' \
task kubernetes:deploy
```

## Use another Minikube profile or namespace

The defaults are:

```text
PROFILE=minikube
NAMESPACE=taskmigo-local
RELEASE=taskmigo
GATEWAY_NAME=taskmigo-local
```

For an isolated profile:

```bash
minikube start -p taskmigo-dev --container-runtime=containerd --cpus=4 --memory=6000m
PROFILE=taskmigo-dev \
NAMESPACE=taskmigo-dev \
GATEWAY_NAME=taskmigo-dev \
task kubernetes:deploy
```

## Rebuild and verify

After changing application source, run the deployment task again:

```bash
task kubernetes:deploy
```

`minikube image build` reuses the in-cluster build cache. The server images are built in sequence so the web and worker
builds can reuse the common multi-stage Gradle build produced by the first server target.

To verify an existing deployment without rebuilding it:

```bash
task kubernetes:verify
```

Run the Helm integration test through Taskfile:

```bash
task kubernetes:test
```

Browser E2E is not a Taskfile task. It requires Node.js 26 and runs independently against any already reachable Taskmigo
environment. See the root `e2e/README.md` for its environment variables and commands.

When a deployment or Helm test fails, print bounded resource descriptions and the last 200 log lines per pod:

```bash
task kubernetes:diagnostics
```

## Reset Taskmigo

Remove Taskmigo, its database, local credentials, and its `GatewayClass` without deleting the Minikube profile:

```bash
task kubernetes:reset
```

Envoy Gateway remains installed because it is a cluster-level controller that another local workload may use.

## Docker driver networking on macOS, Windows, and WSL2

The pipeline uses `taskmigo.internal.com` as one public hostname for the browser, API, and OAuth flow. The hostname must
resolve to the Minikube node IP on the development host; Taskfile supplies the equivalent pod-level mapping to the browser
client for server-side OIDC discovery and token exchange.

With the Docker driver, the node IP is not directly reachable from the host on macOS, Windows, and WSL2. In those
environments, use a network setup that exposes the Gateway address to both the host and cluster workloads, such as
`minikube tunnel`.

Do not change `client.auth.issuer` to a host-only `localhost` port-forward. Taskmigo's browser client performs OIDC work on
the server side, so the issuer must be reachable from both the browser and the client pod.

See the Minikube [accessing applications](https://minikube.sigs.k8s.io/docs/handbook/accessing/) and
[Docker driver](https://minikube.sigs.k8s.io/docs/drivers/docker/) documentation for platform-specific host networking.
