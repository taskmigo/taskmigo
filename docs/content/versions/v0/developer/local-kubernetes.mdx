---
title: Local Kubernetes
description: Build and run the complete Taskmigo stack in Minikube for local development.
---

Use this setup when you need the deployed system rather than one application process. Start a Minikube profile first,
then use one Taskfile pipeline to build and load every image, create local credentials and PostgreSQL, install Envoy
Gateway, deploy the Helm release, and verify the complete stack.

For faster work on one JVM or Node.js process, use [Local development](/docs/v0/developer/local-development) instead.

## What this starts

The local stack contains:

- PostgreSQL `18.4-alpine` inside the Taskmigo namespace;
- Envoy Gateway `1.9.1` as the Gateway API controller;
- the Taskmigo bootstrap Job, which owns Flyway migrations and installation-state reconciliation;
- the Taskmigo web and worker deployments;
- the Taskmigo browser client;
- one `Gateway` plus separate `HTTPRoute` resources for the client and web server.

GitHub Actions starts Minikube with `wait: false`, prepares browser E2E while the cluster starts, then lets Taskfile wait at
the first cluster-dependent operation. Browser E2E is intentionally separate: the `e2e/` package owns Playwright setup and
execution, and CI invokes it directly after the Taskfile-managed deployment is ready.

## Prerequisites

Install these host tools:

- Docker Desktop or Docker Engine with Linux containers and Docker Buildx;
- Minikube;
- Helm 4 or a compatible Helm 3 release;
- [Task](https://taskfile.dev/docs/installation/);
- `curl` for the public endpoint checks.

The pipeline uses Minikube's built-in `kubectl`, so a host `kubectl` installation is not required. Java and Node.js are not
required for deployment because the Dockerfiles build the applications inside containers.

Allocate at least 4 CPUs and 6 GiB of memory to Docker. Start the standard profile before deploying:

```bash
minikube start -p minikube --cpus=4 --memory=6000m
```

## Deploy from a default Minikube profile

With the profile running, run this command from the repository root:

```bash
task kubernetes:deploy
```

`kubernetes:deploy` is an end-to-end, idempotent pipeline. It:

1. Starts image builds while waiting for the selected Minikube profile and node to become ready.
2. Starts PostgreSQL and Envoy Gateway as soon as the cluster is usable, while the images continue building and loading.
3. Waits for PostgreSQL only when the bootstrap Job needs it.
4. Installs or upgrades Taskmigo, waits for the bootstrap hook, and starts the runtime workloads without waiting for their rollouts.
5. Waits for Envoy Gateway and the Taskmigo workloads in parallel.
6. Verifies accepted routes, Flyway state, and both public endpoints.

The default task is an alias for the same pipeline, so `task` also works.

The final output prints the client, API, and API documentation URLs plus the bootstrap login. The default local credentials
are deliberately simple and must never be reused outside a disposable development cluster:

```text
Username: system
Password: taskmigo
```

Credentials are created only when `taskmigo-secrets` does not exist. Override them on the first deployment when needed:

```bash
BOOTSTRAP_USER_PASSWORD='replace-me' \
AUTH_SESSION_SECRET='replace-with-at-least-32-characters' \
task kubernetes:deploy
```

## Use another Minikube profile or namespace

The default values preserve a user's ordinary Minikube profile:

```text
PROFILE=minikube
NAMESPACE=taskmigo-local
RELEASE=taskmigo
GATEWAY_NAME=taskmigo-local
```

Start the profile, then override the deployment variables for an isolated installation:

```bash
minikube start -p taskmigo-dev --cpus=4 --memory=6000m
PROFILE=taskmigo-dev \
NAMESPACE=taskmigo-dev \
GATEWAY_NAME=taskmigo-dev \
task kubernetes:deploy
```

## Rebuild and verify

Run the deployment task again after changing source code. It rebuilds and reloads the fixed local image tags, then performs
a Helm upgrade so the bootstrap hook and runtime rollouts consume the new images:

```bash
task kubernetes:deploy
```

To verify an existing deployment without rebuilding it:

```bash
task kubernetes:verify
```

Run the Helm integration test through Taskfile:

```bash
task kubernetes:test
```

Browser E2E is not a Taskfile task. It requires Node.js 26 and runs independently against any already reachable Taskmigo
environment. From `e2e/`, install and type-check the suite, install Chromium, provide the four `E2E_*` environment variables,
and run `npm test`. See the root `e2e/README.md` for the exact contract and commands.

When a deployment or Helm test fails, print bounded resource descriptions and the last 200 log lines per pod:

```bash
task kubernetes:diagnostics
```

## Reset Taskmigo

Remove Taskmigo, its database, local credentials, and its `GatewayClass` without deleting the user's Minikube profile:

```bash
task kubernetes:reset
```

Envoy Gateway remains installed because it is a cluster-level controller that another local workload may use.

## Docker driver networking on macOS, Windows, and WSL2

The pipeline uses the Minikube node IP and `sslip.io`, so the public hostname is identical for the browser and the client
pod during OIDC discovery and token exchange.

With the Docker driver, the node IP is not directly reachable from the host on macOS, Windows, and WSL2. In those
environments, use a network setup that exposes the Gateway address to both the host and cluster workloads, such as
`minikube tunnel`.

Do not change `client.auth.issuer` to a host-only `localhost` port-forward. Taskmigo's browser client performs OIDC work on
the server side, so the issuer must be reachable from both the browser and the client pod.

See the Minikube [accessing applications](https://minikube.sigs.k8s.io/docs/handbook/accessing/) and
[Docker driver](https://minikube.sigs.k8s.io/docs/drivers/docker/) documentation for platform-specific host networking.
